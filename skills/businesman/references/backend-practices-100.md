# 100 Практик, Алгоритмов и Паттернов Бэкенд-инженера (Backend & Distributed Systems)

Этот справочник содержит 100 прикладных инструментов проектирования высоконагруженных API, работы с базами данных (PostgreSQL), потоковой обработки событий (Kafka), кэширования (Redis), параллелизма, распределенных систем и безопасности для ведущего бэкенд-разработчика (Staff / Principal Backend Engineer).

## Раздел I: Архитектура API, протоколы и сетевые взаимодействия (1–13)

### 1. Идемпотентность всех мутирующих API-операций (Idempotency-Key)
- Реализация заголовка `Idempotency-Key: <UUID>` для всех POST/PUT запросов (финансовые списания, создание заказов):
  - Атомарная фиксация ключа в Redis: `SET idempotency:<key> "PROCESSING" NX EX 120`.
  - Если ключ уже существует и статус `PROCESSING` $\implies$ возврат HTTP 409 Conflict.
  - По завершении бизнес-логики: сохранение HTTP-статуса и тела ответа в Redis на 24 часа.
  - При повторном запросе: мгновенный возврат сохраненного ответа без повторного списания денег.

### 2. Высокопроизводительный gRPC и Protocol Buffers
- Использование gRPC на HTTP/2 для межсервисного взаимодействия:
  - Бинарная сериализация Protobuf в $5–10$ раз быстрее и в $3–4$ раза компактнее JSON.
  - Мультиплексирование сотен запросов в одном TCP-соединении.
  - Строгая двусторонняя типизация интерфейсов через `.proto` файлы.

### 3. Регламент таймаутов на сетевых вызовах (Timeout Discipline)
- Запрет бесконечных блокировок потоков:
  - Client Connect Timeout: $\le 1$ сек.
  - Read/Write Timeout: $\le 5$ сек.
  - Database Query Timeout: $\le 2–3$ сек (`statement_timeout`).
  - Внешний API Timeout: $\le 3$ сек с гарантированным fallback-сценарием.

### 4. Паттерн автоматического выключателя (Circuit Breaker)
- Изоляция сбойных внешних зависимостей (банки, интеграторы, геокодеры):
  - Состояние `Closed`: запросы идут нормально.
  - При достижении 50% ошибок за скользящее окно $\implies$ переход в `Open`: мгновенный возврат ошибки или кэша без отправки запроса в сеть на 30 секунд.
  - Состояние `Half-Open`: пропуск одного пробного запроса для проверки восстановления сервиса.

### 5. Экспоненциальный бэкофф с полным джиттером (Full Jitter Exponential Backoff)
- Формула повторов при сбоях, исключающая синхронный шквал повторных запросов на упавший сервис:
  $$T_{\text{sleep}} = \text{random}(0, \min(T_{\max}, T_{\text{base}} \times 2^{\text{attempt}}))$$
- Добавление случайности (джиттера) равномерно размазывает нагрузку во времени.

### 6. Стандарт ошибок RFC 7807 (Problem Details for HTTP APIs)
- Единый машиночитаемый формат описания ошибок в формате `application/problem+json`:
  ```json
  {
    "type": "https://api.company.com/errors/insufficient-funds",
    "title": "Недостаточно средств",
    "status": 422,
    "detail": "Баланс счета 500 руб. меньше суммы списания 1200 руб.",
    "instance": "/orders/1234/pay"
  }
  ```

### 7. Потоковая отдача ответов через Server-Sent Events (SSE)
- Реализация потоковой передачи текстовых токенов генерации LLM через `text/event-stream`: заголовок `Cache-Control: no-cache`, `X-Accel-Buffering: no` (отключение буферизации Nginx) для достижения задержки первого токена $<300$ мс.

### 8. Алгоритмы ограничения частоты запросов (Rate Limiting)
- Внедрение Token Bucket и Sliding Window Counter на шлюзе API:
  - Ограничение по API-ключу, IP-адресу или Tenant ID.
  - При превышении лимита — возврат HTTP 429 Too Many Requests с информативными заголовками `X-RateLimit-Limit`, `X-RateLimit-Remaining` и `Retry-After`.

### 9. Паттерн Bulkhead (Отсеки непотопляемости)
- Разделение пулов соединений и потоков по критичности: падение сервиса формирования второстепенных PDF-отчетов физически не может исчерпать пул потоков, обслуживающий оформление заказов и прием платежей.

### 10. Лимиты сложности в GraphQL (Query Complexity Analysis)
- Если в проекте используется GraphQL: обязательный статический анализ глубины (Max Depth $\le 6$) и расчет веса запроса (Query Cost) до его выполнения для предотвращения DoS-атак через циклические вложенные запросы.

### 11. Двусторонний стриминг и WebSockets
- Использование WebSockets для интерактивных систем реального времени (коллаборативные редакторы, биржевые стаканы): управление пулом соединений через брокер сообщений (Redis Pub/Sub) для рассылки сообщений между нодами кластера.

### 12. Сжатие трафика Brotli/Gzip с порогом размера
- Включение сжатия ответов API строго для тел размером $>1024$ байт (сжатие мелких ответов только увеличивает размер за счет заголовков и сжигает CPU).

### 13. Изоляция контекста запроса (Context Propagation)
- Проброс `context.Context` (в Go) через все слои сервиса: если клиент прервал соединение (закрыл вкладку), контекст мгновенно отменяется, что автоматически останавливает тяжелый SQL-запрос в базе данных, сберегая ресурсы сервера.

## Раздел II: Реляционные базы данных и транзакции (PostgreSQL) (14–26)

### 14. Уровни изоляции транзакций в PostgreSQL
- Осознанный выбор уровня изоляции под задачу:
  - *Read Committed (По умолчанию):* Видны только закоммиченные данные. Подходит для 90% CRUD-операций.
  - *Repeatable Read:* Гарантирует снимок данных на момент старта транзакции. Защищает от неповторяющегося чтения.
  - *Serializable:* Полная иллюзия последовательного выполнения. Защищает от аномалий сериализации (Write Skew) в финансовых операциях (требует обработки ошибок 40001 serialization_failure с повтором транзакции).

### 15. Пуллеры соединений: PgBouncer в режиме Transaction Pooling
- База данных Postgres выделяет отдельный системный процесс на каждое соединение.
- Установка PgBouncer перед базой: 10 000 клиентских соединений обслуживаются пулом из 50–100 реальных соединений к Postgres, снижая потребление RAM и переключение контекста процессора в разы.

### 16. Оптимизация индексов: Частичные и покрывающие индексы
- **Partial Indexes:** `CREATE INDEX idx_orders_unpaid ON orders(created_at) WHERE status = 'unpaid';` — индексирует только 2% активных неоплаченных заказов вместо 100 млн закрытых, размер индекса сокращается в 50 раз.
- **Covering Indexes:** `CREATE INDEX idx_users_email ON users(email) INCLUDE (id, full_name);` — обеспечивает Index-Only Scan без обращения к страницам таблицы (heap fetch).

### 17. Анализ планов запросов EXPLAIN (ANALYZE, BUFFERS)
- Чтение реального выполнения запросов:
  - Поиск `Seq Scan` на больших таблицах.
  - Сравнение `actual rows` с `estimated rows` (при расхождении — запуск `ANALYZE table_name` для обновления статистики планировщика).
  - Контроль `Buffers: shared read` (дисковые чтения) против `shared hit` (чтения из оперативной памяти).

### 18. Паттерн Transactional Outbox
- Гарантия надежной доставки событий в Kafka/RabbitMQ без двухфазных коммитов:
  ```sql
  BEGIN;
  INSERT INTO orders (id, user_id, amount) VALUES (1, 42, 5000);
  INSERT INTO outbox_events (event_id, aggregate_type, payload) 
  VALUES ('uuid', 'OrderCreated', '{"order_id": 1, "amount": 5000}');
  COMMIT;
  ```
- Отдельный фоновый процесс (или Debezium CDC) вычитывает таблицу `outbox_events` и надежно отправляет сообщения в очередь сообщений.

### 19. Декларативное партиционирование таблиц (Partitioning)
- Разбивка таблиц объемом $>50$ млн строк (логи, события, финансовые проводки) по диапазонам дат (`PARTITION BY RANGE (created_at)`). Позволяет мгновенно удалять старые данные за секунду через `DROP TABLE partition_name` вместо медленного `DELETE`, порождающего bloat.

### 20. Настройка параметров автовакуума (Autovacuum Tuning)
- Предотвращение деградации производительности Postgres:
  - Уменьшение `autovacuum_vacuum_scale_factor` с 0.2 до 0.05 на быстрорастущих таблицах.
  - Увеличение `maintenance_work_mem` до 1–2 ГБ для ускорения очистки мертвых строк.

### 21. Ликвидация взаимных блокировок (Deadlock Prevention)
- Правило архитекторов: если транзакция обновляет несколько строк в таблице, она обязана обновлять их **в строго одинаковом детерминированном порядке** (например, упорядочив массив ID по возрастанию: `SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE`).

### 22. Защита от долгоживущих транзакций
- Жесткая настройка параметров безопасности в `postgresql.conf`:
  - `statement_timeout = '5s'` (убийство зависших запросов).
  - `idle_in_transaction_session_timeout = '10s'` (убийство брошенных транзакций, удерживающих блокировки).
  - `lock_timeout = '2s'` (быстрый отказ, если замок не может быть получен).

### 23. Безопасное добавление колонок с дефолтными значениями
- В Postgres $\ge 11$ добавление колонки `ALTER TABLE users ADD COLUMN is_verified boolean DEFAULT false;` не переписывает таблицу и выполняется мгновенно (Metadata-only change). Для старых версий или тяжелых вычислений — паттерн Expand and Contract.

### 24. Оптимистичные блокировки (Optimistic Locking via Version)
- Контроль конкурентного изменения записи:
  `UPDATE products SET stock = stock - 1, version = version + 1 WHERE id = 42 AND version = 5;`
- Если запрос вернул 0 измененных строк, значит другой процесс уже обновил запись — транзакция откатывается и повторяется заново.

### 25. Потоковая репликация и Patroni Failover
- Развертывание кластера Postgres высокой доступности: мастер + 2 асинхронные реплики под управлением Patroni и etcd. Автоматический выбор нового лидера при сбое мастера за $<15$ секунд без потери консистентности.

### 26. Мониторинг bloat и раздувания таблиц
- Регулярный замер процента мертвого места в таблицах и индексах. Использование утилиты `pg_repack` для переупаковки таблиц и перестроения индексов на лету без блокировок чтения и записи.

## Раздел III: Очереди, стриминг и брокеры сообщений (Kafka & RabbitMQ) (27–38)

### 27. Гарантии доставки: Семантика At-Least-Once
- В распределенных системах единственный надежный способ доставки — **At-Least-Once (Хотя бы один раз)**:
  - Продьюсер отправляет сообщение и ждет подтверждения (`acks=all` в Kafka).
  - Консьюмер подтверждает обработку (`manual ack`) строго **после** успешной записи в базу данных.
  - Из-за сетевых сбоев сообщения могут дублироваться, поэтому консьюмер обязан быть идемпотентным.

### 28. Проектирование ключей партиционирования в Kafka (Partition Keys)
- Сообщения внутри одной партиции Kafka упорядочены строго последовательно.
- Выбор ключа: `user_id` или `order_id` в качестве ключа гарантирует, что все события по конкретному клиенту обрабатываются строго по порядку, но параллельно с другими пользователями.

### 29. Идемпотентный консьюмер (Deduplication Layer)
- Проверка уникальности сообщения перед обработкой:
  ```sql
  INSERT INTO processed_messages (message_id, processed_at) 
  VALUES ('msg-uuid-123', NOW()) 
  ON CONFLICT (message_id) DO NOTHING;
  ```
- Если запись уже существует, воркер подтверждает сообщение брокеру и пропускает повторную бизнес-логику.

### 30. Карантинная очередь Dead Letter Queue (DLQ)
- Если при обработке сообщения возникает непредвиденная ошибка бизнес-логики (битый JSON, некорректные данные):
  - Повтор (Retry) с экспоненциальной задержкой до 3–5 раз.
  - При повторных сбоях сообщение отправляется в очередь `DLQ_orders` с сохранением стека ошибки, а основная очередь продолжает работать без остановки конвейера.

### 31. Потоковый захват изменений Change Data Capture (Debezium)
- Чтение WAL-логов Postgres демоном Debezium: автоматическая трансляция всех событий создания, обновления и удаления строк в топики Kafka за $<10$ мс без нагрузки на саму базу данных.

### 32. Мониторинг отставания консьюмеров (Consumer Lag)
- Ключевая метрика брокера: отставание консьюмера от головы топика (Lag в количестве сообщений). При росте лага система автоматически масштабирует количество реплик воркеров (KEDA автоскейлинг в Kubernetes).

### 33. Сжатие сообщений в Kafka: zstd
- Включение компрессии на стороне продьюсера (`compression.type = zstd`): уменьшение сетевого трафика и размера хранилища на дисках брокеров на 60–75% при минимальной нагрузке на CPU.

### 34. Разделение тяжелых вложений (Claim-Check Pattern)
- Запрет пересылки файлов размером $>1$ МБ через Kafka/RabbitMQ: файл загружается в объектное хранилище S3, а в сообщение помещается только ссылка и хэш (`{ "file_url": "s3://...", "sha256": "..." }`).

### 35. Управление топологией очередей в RabbitMQ
- Использование Topic Exchange: гибкая маршрутизация сообщений по маскам ключей (например, `orders.eu.created`, `orders.us.cancelled`), позволяющая подключать новые сервисы-слушатели без изменения кода отправителя.

### 36. Эволюция схем в Schema Registry (Protobuf / Avro)
- Проверка совместимости схем (BACKWARD compatibility): продюсер не может отправить сообщение с измененной структурой данных, пока CI не проверит, что старые запущенные консьюмеры смогут его прочитать.

### 37. Обработка сигналов перегрузки (Backpressure)
- Консьюмер контролирует скорость чтения: если локальная очередь задач заполнена на 80%, поток временно приостанавливает вычитку сообщений из брокера (`consumer.pause()`), давая воркерам обработать накопившиеся данные.

### 38. Распределенные саги: Оркестрация через Temporal
- Реализация многошаговых процессов (заказ такси, бронирование отеля): использование специализированных оркестраторов с сохранением состояния (Temporal / Cadence), гарантирующих надежное выполнение компенсирующих транзакций при сбоях на любом шаге.

## Раздел IV: Кэширование и In-Memory хранилища (Redis) (39–51)

### 39. Стратегия Cache-Aside (Lazy Loading)
- Стандарт работы с кэшем:
  1. Чтение из Redis по ключу.
  2. Если кэш есть (Cache Hit) $\implies$ возврат данных.
  3. Если кэша нет (Cache Miss) $\implies$ чтение из Postgres, запись в Redis с TTL, возврат клиенту.

### 40. Защита от Cache Stampede: Алгоритм XFetch
- Вероятностное раннее обновление кэша до истечения срока TTL:
  $$\Delta \times \beta \times \ln(\text{random}()) > \text{TTL} - \text{now}$$
  Один из случайных параллельных запросов фоново инициирует обновление кэша из БД за несколько секунд до его истечения, предотвращая пробитие базы миллионом пользователей в момент обнуления ключа.

### 41. Защита от пробития кэша несуществующими ключами (Cache Penetration)
- Если клиент запрашивает сущность, которой нет в базе данных:
  - Сохранение в Redis пустого значения (`null`) с коротким временем жизни (TTL 60 сек).
  - Использование фильтра Блума (Bloom Filter) на входе: если фильтр говорит «элемента точно нет», запрос к БД даже не выполняется.

### 42. Защита от лавины кэша (Cache Avalanche Mitigation)
- Категорический запрет устанавливать одинаковый жесткий TTL для миллионов записей. Добавление случайного разброса (Jitter):
  `TTL = base_ttl + rand(-0.1 * base_ttl, +0.1 * base_ttl);`

### 43. Распределенный замок Redlock с автоматическим продлением
- Захват блокировки в Redis: `SET lock:<resource> <uuid> NX PX 10000`.
- Запуск фонового таймера (Watchdog), продлевающего аренду замка каждые 3 секунды, пока задача выполняется.
- Освобождение замка строго через Lua-скрипт с проверкой UUID владельца.

### 44. Скользящий Rate Limiter на Sorted Sets (ZSET)
- Точный лимит запросов в скользящем окне:
  - Добавление текущего timestamp в ZSET: `ZADD ratelimit:<ip> <now> <now>`.
  - Удаление устаревших записей: `ZREMRANGEBYSCORE ratelimit:<ip> 0 <now - window>`.
  - Подсчет оставшихся: `ZCARD ratelimit:<ip>`. Все выполняется одним атомарным конвейером (Pipeline/Lua).

### 45. Политика вытеснения памяти Redis: `volatile-lfu`
- При исчерпании выделенной оперативной памяти (Maxmemory): вытеснение наименее часто используемых ключей (Least Frequently Used) только среди тех, у которых установлен TTL, защищая персистентные конфигурационные ключи.

### 46. Сериализация данных: MessagePack вместо JSON
- Использование MessagePack для хранения сложных структур в Redis: бинарный формат экономит до 40% памяти RAM и парсится процессором в 3 раза быстрее JSON.

### 47. Запрет команды `KEYS *` в продакшне
- Команда `KEYS *` блокирует главный поток Redis на секунды. Переименование опасных команд в `redis.conf` (`rename-command KEYS ""`). Для поиска ключей используется строго итеративный курсор `SCAN`.

### 48. Использование Redis Hashes для экономии памяти
- Хранение сущностей (профиль пользователя, настройки) в виде Hash-таблиц (`HSET user:123 name "..." email "..."`), использующих сжатую память ziplist при небольшом количестве полей.

### 49. Инвалидация кэша по тегам (Tag-based Invalidation)
- Привязка ключей к тегам сущностей: при обновлении профиля компании инвалидируются все кэши, помеченные тегом `company:42`, без необходимости ручного перечисления десятков зависимых ключей.

### 50. In-Memory кэширование на уровне процесса приложения (Go Ristretto)
- Двухуровневое кэширование (L1 process memory $\to$ L2 distributed Redis): неизменяемые справочники хранятся прямо в оперативной памяти процесса с временем доступа $<1$ микросекунды.

### 51. Контроль больших ключей (Bigkeys Audit)
- Регулярный запуск `redis-cli --bigkeys`: поиск аномальных списков или хешей, занимающих более 5 МБ памяти, и их принудительное шардирование.

## Раздел V: Конкурентность, параллелизм и многопоточность (52–64)

### 52. Управление жизненным циклом горутин (Zero Goroutine Leaks)
- Каждая запускаемая горутина/поток обязана иметь гарантированную точку выхода:
  - Передача `context.Context` с таймаутом.
  - Чтение из каналов с использованием `select` и ветки `case <-ctx.Done(): return`.

### 53. Паттерн Worker Pool
- Ограничение параллелизма: вместо создания 100 000 горутин на 100 000 задач, создается фиксированный пул из $N$ воркеров (равный числу CPU ядер или лимиту соединений к БД), разбирающих задачи из буферизованного канала.

### 54. Повторное использование памяти через пулы объектов (`sync.Pool`)
- Снижение нагрузки на сборщик мусора (GC): аллокация тяжелых байтовых буферов и структур в `sync.Pool`. Буфер берется из пула, используется для парсинга запроса, очищается и возвращается в пул без выделения новой памяти в heap.

### 55. Атомарные операции вместо тяжелых мьютексов
- Для счетчиков метрик, генераторов ID и флагов состояний: использование процессорных инструкций CAS (Compare-And-Swap) через `sync/atomic` (в 10 раз быстрее стандартного `sync.Mutex`).

### 56. Читательские мьютексы (RWMutex Discipline)
- Если данные читаются 1000 раз в секунду, а обновляются раз в час: использование `sync.RWMutex`. Метод `RLock()` позволяет тысячам потоков читать данные параллельно без взаимных блокировок.

### 57. Пакетная агрегация на лету (Batching Dispatcher)
- Склейка одиночных вызовов: сервис накапливает входящие события в буфер в течение 10 мс (или до накопления 100 элементов) и отправляет в базу данных один пакетный запрос `INSERT ... VALUES (...), (...)`, повышая пропускную способность в $10\times$ раз.

### 58. Корректная остановка сервиса (Graceful Shutdown)
- Перехват системных сигналов операционной системы:
  ```go
  quit := make(chan os.Signal, 1)
  signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
  <-quit
  ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
  defer cancel()
  server.Shutdown(ctx)
  ```
- Сервер перестает принимать новые HTTP-запросы, закрывает соединения и дожидается завершения фоновых задач до принудительного убийства процесса.

### 59. Защита от утечек дескрипторов (Resource Leaks Prevention)
- Использование конструкции `defer` для немедленного освобождения ресурсов:
  `resp, err := client.Do(req); if err == nil { defer resp.Body.Close(); io.Copy(io.Discard, resp.Body) }`
- Чтение остатков тела обязательно для переиспользования TCP-соединения через HTTP Keep-Alive.

### 60. Профилирование боевой производительности (pprof & Pyroscope)
- Подключение эндпоинта отладки: сбор профилей CPU, аллокаций памяти и блокировок мьютексов под реальной боевой нагрузкой для поиска неоптимальных регулярных выражений и лишних копирований массивов.

### 61. Настройка сборщика мусора (Go GC Tuning via GOGC & GOMEMLIMIT)
- Тонкая настройка рантайма: установка `GOMEMLIMIT` предотвращает падение контейнера по OOM (Out Of Memory) в Kubernetes, динамически снижая интервал сборки мусора при приближении к границе памяти.

### 62. Ограничение конкурентных обращений к внешним сервисам (Semaphore Pattern)
- Использование взвешенного семафора (`semaphore.Weighted`): ограничение количества одновременных сетевых запросов к партнерскому API (не более 20 параллельных запросов), защищающее от бана по IP.

### 63. Быстрая сериализация JSON: `sonic` / `easyjson`
- Замена стандартного рефлексивного парсера `encoding/json` на кодогенерацию или JIT-ассемблерный парсер (`bytedance/sonic`), ускоряющий разбор JSON в 4–8 раз.

### 64. Изоляция параллельных тестов и детектор гонок (`-race`)
- Обязательный запуск тестов в CI/CD с флагом `-race` (Race Detector): немедленный провал билда при обнаружении несинхронизированного доступа к общей переменной из разных потоков.

## Раздел VI: Распределенные системы и отказоустойчивость (65–76)

### 65. Генерация уникальных сортируемых ID: UUIDv7 / Snowflake
- Отказ от устаревших случайных UUIDv4 (которые фрагментируют B-Tree индексы баз данных).
- Использование **UUIDv7**: первые 48 бит содержат Unix-timestamp миллисекунд. Новые записи ложатся строго в конец индекса, обеспечивая идеальную производительность вставок при сохранении глобальной уникальности.

### 66. Разрешение конфликтов в распределенных данных (Last-Write-Wins vs CRDT)
- Выбор стратегии: для простых сущностей — фиксация временных меток (LWW с синхронизацией часов по NTP). Для совместного редактирования — бесконфликтные реплицируемые типы данных (CRDT).

### 67. Консенсус и распределенная координация (Raft via etcd)
- Использование etcd / Consul для хранения конфигураций, обнаружения сервисов (Service Discovery) и выбора лидера (Leader Election) на базе строгого математического консенсуса Raft.

### 68. Согласованное хеширование (Consistent Hashing)
- Распределение ключей по узлам распределенного кэша или хранилища: добавление или удаление одной ноды требует перемещения строго $1/N$ части ключей, исключая полную инвалидацию кластера.

### 69. Протоколы Health Check: Liveness против Readiness
- Разделение проверок здоровья в Kubernetes:
  - `/healthz` (Liveness): проверяет, жив ли сам процесс (если нет $\implies$ перезапуск контейнера).
  - `/ready` (Readiness): проверяет готовность обрабатывать трафик (связь с БД, прогрев кэшей; если нет $\implies$ трафик временно снимается, но контейнер не перезапускается).

### 70. Трассировка запросов через OpenTelemetry (Context Propagation)
- Внедрение сквозного трейсинга: извлечение заголовка `traceparent` (W3C standard) на входе в сервис и его обязательная передача во все исходящие HTTP- и gRPC-запросы и события Kafka.

### 71. Балансировка нагрузки: Алгоритм Power of Two Choices (P2C)
- Выбор целевого сервера для отправки запроса: случайный выбор 2 серверов из пула и отправка запроса тому из них, у которого меньше активных соединений (Least Loaded). Предотвращает появление перегруженных «горячих» узлов.

### 72. Разделение чтения и записи на уровне роутинга (Read/Write Splitting)
- Балансировщик на уровне приложения: мутирующие запросы (`INSERT/UPDATE/DELETE`) направляются на мастер-ноду Postgres, а запросы на чтение (`SELECT`) балансируются между репликами.

### 73. Управление конфигурацией без перезапуска (Dynamic Config Reload)
- Подписка на изменения конфигурации в etcd/Consul или чтение сигналов SIGHUP: обновление параметров логирования, лимитов и флагов фичей на лету за 100 мс без перезапуска приложения.

### 74. Защита от сетевых разделений (Split-Brain Prevention)
- Правило нечетного кворума: любой распределенный кластер (etcd, Zookeeper, Patroni) состоит из нечетного числа узлов ($2N + 1$, минимум 3). При сетевом разделении функционировать продолжает только тот сегмент, который видит строго $>50\%$ голосов.

### 75. Автоматическое самовосстановление (Self-Healing Workers)
- Фоновые демоны-супервизоры: при падении рабочего потока с фатальной паникой — перехват `recover()`, логирование трассировки стека, отправка алерта в Sentry и автоматический перезапуск воркера.

### 76. Финальный чеклист отказоустойчивости бэкенда (Backend Resilience Gate)
- Контрольный список готовности к пиковым нагрузкам:
  - [ ] Все мутирующие эндпоинты защищены `Idempotency-Key`.
  - [ ] На всех внешних вызовах настроены таймауты и Circuit Breakers.
  - [ ] Пул соединений к БД работает через PgBouncer, `statement_timeout` активен.
  - [ ] Доставка сообщений в очереди построена по паттерну Transactional Outbox.
  - [ ] Воркеры идемпотентны, ошибки уходят в DLQ.
  - [ ] Кэш защищен от Stampede (XFetch), Avalanche (Jitter) и Penetration.
  - [ ] Реализован Graceful Shutdown с тайм-аутом до 15 секунд.
  - [ ] Эндпоинты `/healthz` и `/ready` корректно проверяют зависимости.
