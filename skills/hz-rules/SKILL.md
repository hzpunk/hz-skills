# Глобальные правила разработки HZ (Артём)

## 1. Админка = Графики с первого дня (`hz-admin-charts`)
- При создании/модернизации админки сразу делать наглядную аналитику (карточки метрик + графики / гистограммы).
- Переключатель периода: **День / Неделя / Месяц / Квартал / Год** — данные на графиках пересчитываются.
- Адаптированность под Desktop и Mobile.

## 2. Формы = Модалки (`hz-forms-as-modals`)
- Если это **не лендинг** и пользователь **не просил** форму прямо на странице — **не** рисовать карточку/блок с полями в основном layout.
- Кабинет, админка, дашборд, CMS -> кнопка **Добавить** + всплывающее окно (модалка / Dialog / Drawer).
- Все публичные формы строго защищаются по стандарту `hz-forms-anti-bot` (5 уровней: honeypot, timing >= 5s, JS challenge токен, IP+Fingerprint rate limit, серверный silent drop).

## 3. Краткие ответы (`hz-brief-responses`)
- Без лишних слов и длинных объяснений.
- В конце ответа — **одна короткая строка**: что сделано или что нужно сделать пользователю.

## 4. Сразу Git Commit после изменений (`hz-commit-after-global`)
- После завершения логического куска работы — сразу делать `git commit` (без `git push`, пока не попросят).
- Осмысленное сообщение коммита на русском или английском.

## 5. Домены из deploy/DNS (`hz-domains-from-deploy`)
- Публичный URL брать только из фактического deploy / DNS / config. Не придумывать домены.

## 6. Синхронизация Env после коммита (`hz-env-sync-after-commit`)
- Не коммитить `.env` / секреты. При необходимости синхронизировать ключи через утилиты/скрипты.

## 7. Обучение на ошибках (`hz-learn-from-mistakes`)
- При замечаниях не спорить. Уточнить факт, переделать, дождаться подтверждения пользователя перед фиксацией правила.

## 8. Live Production Truth (`hz-verify-live-before-claiming`)
- Не утверждать состояние production по скриншоту — сначала лив-проверка (`curl`, деплой, стейт).

## 9. Сохранение палитры темы проекта (`hz-theme-palette`)
- **Строго запрещено** перебивать оригинальную цветовую гамму проекта кастомными hardcoded-цветами (например `slate-950`, `slate-900`, `zinc-900`).
- Использовать исключительно семантические CSS-переменные/классы темы проекта (`bg-background`, `text-foreground`, `bg-card`, `bg-muted`, `border-border`, `bg-primary`, `text-primary-foreground`).

## 10. Кастомные UI компоненты и диалоги вместо нативных браузерных (`hz-custom-ui-components`)
- **Строго запрещено** использовать нативные системные диалоги браузера (`confirm()`, `alert()`, `prompt()`), а также нативные HTML выпадающие списки (`<select>`).
- Все диалоги подтверждения действий/удаления, уведомления об ошибках и селекторы изготавливать исключительно кастомными всплывающими модальными окнами и алертами на Tailwind/React в дизайне темы проекта.

## 12. Мобильный App-like UX (`hz-mobile-first-app-like`)
- Мобильная версия сайта обязана проектироваться и ощущаться как нативное мобильное приложение.
- Эргономика под большой палец, крупные зоны нажатия (тач-таргеты от 44px), компактные плавающие панели/доки, выдвижные шторки (Drawer) вместо выпадающих меню, нулевой горизонтальный скролл.

## 13. Юридическая основа и безопасность бизнеса (`hz-legal-compliance`)
- Все формы сбора контактов и заявок **строго обязаны** содержать юридический базис: дисклеймер / чекбокс согласия на обработку персональных данных в соответствии с 152-ФЗ РФ.
- Обязательно наличие ссылки/модального окна с «Политикой конфиденциальности» и указанием официальных реквизитов организации (ООО «ЭЙЧЗЕТКОМПАНИ») для полного исключения юридических и финансовых рисков.

## 14. Микроинтерактивность каждого элемента (`hz-micro-interactions`)
- Каждый интерактивный и информационный элемент на странице должен давать плавный тактильный/визуальный отклик (hover-состояния, мягкий `active:scale-[0.97]`, акцентные фокусы). Никаких мертвых статичных кнопок.

## 15. Стандарты верстки и предотвращения Layout Shifts (`hz-zero-jitter-architecture`)
- **Разделение CSS-позиционирования и Framer Motion**: Никогда не анимировать `x/y/scale` на элементах с классами CSS-трансформа (`-translate-x-1/2`). Использовать статичный родительский wrapper.
- **Zero-Jitter Inactive**: Для неактивных состояний секций (`inactive`) анимировать только `opacity` без сдвига координат `y` и масштаба `scale`.
- **Zero First-Render Flash**: Использовать `initial={false}` для секций первого экрана, чтобы избежать мерцания контента при гидратации.
- **Динамические коллекции**: Все списки рендерить строго через `.map()` из единого источника (`site.ts`), не завязываясь на фиксированные индексы `list[0]`.

## 16. Упреждающие уточнения и устранение двусмысленности (`hz-proactive-clarifications`)
- **Запрет на слепое додумывание**: Если в задаче не хватает критических данных, формулировка допускает двоякое толкование или есть развилка в архитектуре/дизайне/контенте — **категорически запрещено молча угадывать**.
- **Проактивные вопросы ДО написания кода**: Заранее обратиться к пользователю с конкретными вопросами (через `ask_question` или четкие варианты на выбор), подсвечивая скрытые риски и пробелы (юридическая чистота, реквизиты, мобильные сценарии, недостающие тексты).

## 17. Документация концепции DESIGN.md (`hz-design-doc-first`)
- На старте проекта или фичи создавать и поддерживать `DESIGN.md` в корне репозитория.
- Вся верстка, типографика, адаптивные сетки и палитра ведутся строго по зафиксированной в `DESIGN.md` дизайн-системе.

## 18. Полиморфные адаптивные компоненты (`hz-polymorphic-adaptive-components`)
- Создавать переиспользуемые компоненты, способные кардинально трансформировать свой внешний вид (от минималистичного списка до объемной карточки или аккордеона) под контекст без дублирования бизнес-логики.

## 19. Прагматичный анти-ИИ текст и продажи (`hz-anti-ai-slop-pragmatism`)
- **Запрет на ИИ-клише и воду**: Категорически исключить бессодержательный пафос («в эпоху перемен», «синергия решений», «инновационная парадигма») и шаблонные одинаковые 3-колоночные сетки с абстрактными иконками.
- **Материалистический расчет**: Текст и структура проекта должны **продавать** (товар, услугу, партнерство). Только твёрдая польза, конкретные цифры, условия, факты и проверяемый экономический результат.

## 20. Производственный бизнес-цикл, SEO, GEO, GGO и OpenGraph (`hz-production-business-lifecycle`)
- **Бизнес-цели и экономия ресурсов**: На этапе подготовки четко формулировать цель страницы, портрет ЦА и воронку конверсии. Использовать архитектуру с минимальным Time-to-Market и нулевыми лишними затратами на инфраструктуру.
- **SEO & Core Web Vitals**: Семантическая верстка, валидная микроразметка Schema.org (`Person`, `Organization`), `sitemap.xml`, `robots.txt`, идеальные показатели загрузки (0 CLS, быстрый LCP).
- **GEO-привязка**: Явное указание региона присутствия бизнеса (РФ, Москва, федеральный охват).
- **GGO (Generative Engine Optimization)**: Структурирование фактов под ИИ-поисковики (Perplexity, ChatGPT Search, Яндекс Нейро, Gemini) для быстрого цитирования без галлюцинаций.
- **OpenGraph & Мессенджеры**: Сочные мета-теги `og:title`, `og:description`, привлекательный `og:image` (1200×630) для презентабельного вида при отправке ссылок в Telegram, WhatsApp и соцсети.

## 21. Тонкая эстетика интерактивных эффектов (`hz-refined-interactions`)
- Любые анимации, следы или интерактивные эффекты обязаны быть деликатными, статусными и выверенными, без дешевых шаблонных брызг и навязчивых частиц.

## 22. Запрет на удаление без согласования (`hz-ask-before-delete`)
- **Никогда не удалять функционал вслепую**: Если пользователь говорит, что элемент выглядит неудачно («кринжово», «не нравится»), **строго запрещено молча вырезать код под корень**.
- **Обязательное интервью перед удалением**:
  1. Спросить: «Удалить полностью или исправить/переделать?»
  2. Если переделать — задать конкретные вопросы: «Как именно вы хотите это видеть? (вариант А, Б, В)».
- Вносить изменения только после прямого ответа пользователя.

## 23. Округлая плавающая мобильная навигация и Zero-Reflow динамика (`hz-mobile-dynamic-pill-dock`)
- **Форм-фактор**: Мобильные нижние навигационные панели (Bottom Docks / Pills) проектируются как плавающий округлый остров (floating pill / island) с отступами от краев экрана, в единой дизайн-системе с верхними элементами интерфейса.
- **Zero-Reflow скролл-динамика**: Любая динамическая реакция навигационной панели при скролле (сжатие, скрытие, минимизация) обязана производиться **исключительно через аппаратные GPU-свойства** (`transform: scale()`, `transform: translateY()`, `opacity`).
- **Запрет layout thrashing при скролле**: Категорически запрещено монтировать/размонтировать DOM-узлы, анимировать `height: auto` или изменять габариты дочерних кнопок во время пролистывания.
- **Стабильная геометрия**: Размеры тач-зон и ячеек остаются геометрически стабильными; сжатие реализуется общим масштабированием контейнера (`scale: 0.9–0.92`) с дебаунсом не менее 350–400 мс для исключения стробоскопического дергания при инерционном скролле.

## 24. Мобильная эргономика, читаемость и запрет микро-шрифтов (`hz-mobile-first-readability`)
- **Запрет микро-шрифтов**: На мобильных экранах (`< 768px`) категорически запрещено использовать микро-размеры шрифтов (`8px`, `9px`, `10px`) для любого смыслового текста.
  - Основной текст (body / параграфы): **не менее 14–16px** (`text-sm` / `text-base`, `leading-relaxed`).
  - Метаданные, теги, бейджи и подписи: **не менее 12px** (`text-xs`).
  - Заголовки (H1–H3): гармоничные пропорции под мобильный вьюпорт (**20–28px**, без ломаных переносов).
- **Свободный поток и воздух**: Запрещено сжимать мобильные экраны многослойными вложенными карточками («карточка в карточке в карточке») и тесными внутренними рамками. Контент должен читаться естественно и свободно, как в качественном редакционном издании или нативном приложении.
- **Полноценная нативная прокрутка**: Отказ от искусственных внутренних `overflow: auto` контейнеров на мобильных устройствах в пользу естественного потока документа, позволяющего мобильному браузеру корректно управлять адресной строкой и инерцией.

## 25. Сквозная навигационная согласованность на всех маршрутах (`hz-global-consistent-navigation`)
- На всех маршрутах и страницах проекта (главная, архивы, детальные страницы, формы, вспомогательные разделы) обязана сохраняться общая дизайн-система навигации: доступность глобального хедера, предсказуемый возврат на верхний уровень и согласованная мобильная навигация.

## 26. Стандарты поисковой оптимизации, метаданных и краулинга (`hz-seo-crawler-audit-standards`)
- **Длина Meta Title (строго до 60 символов)**:
  - Заголовки страниц (`title` / `metaTitle`) обязаны укладываться в диапазон **до 60 символов**.
- **Длина Meta Description (строго 120–160 символов)**:
  - Мета-описания страниц на всех индексируемых маршрутах обязаны содержать **от 120 до 160 символов**.
- **Чистый Noindex для приватных зон**:
  - Служебные разделы обязаны содержать явный запрет индексации.

## 27. Синхронизация Руководства Пользователя при любых изменениях UI (`hz-sync-user-guide-on-ui-change`)
- **Обязательное обновление документации при любых изменениях UI**: При внесении любых изменений в интерфейс, добавлении новых графиков (в т.ч. свечных графиков P&L), экранов, модальных окон, кнопок или страниц — **строго обязательно сразу актуализировать Руководство Пользователя** в интерактивном компоненте (`components/user-guide-content.tsx`), артефакте `user_guide.md` и файле правил `rules/hz-sync-user-guide.mdc`.

## 28. Полный запрет моковых кнопок быстрого входа и хардкода учетных данных в UI (`hz-no-mock-quick-logins`)
- **Строжайший запрет**: Категорически запрещено добавлять в интерфейсы (формы логина, модалки авторизации, гейткиперы админки) кнопки «Быстрый вход», «Войти как админ», автозаполнение паролей/логинов и любые другие демонстрационные кнопки.
- **Аутентичный продакшен**: Авторизация обязана быть строго реальной: только чистые поля ввода Email и Пароля без подсказок, захардкоженных тестовых аккаунтов и демонстрационных шорткатов.

## 29. Категорический запрет ссылок на изображения вместо загрузки файлов (`hz-direct-file-upload-only`)
- **Строжайший запрет**: Категорически запрещено заставлять пользователя вставлять URL/ссылки на изображения (`https://...`) при смене аватара, загрузке фотографий в профиль, публикации постов или создании событий.
- **Только прямая загрузка с устройства**: Любая форма добавления/смены изображений обязана предоставлять прямую нативную загрузку файла с устройства (`<input type="file" accept="image/*" />`, Drag-and-Drop, выбор из галереи или камеры смартфона).
## 30. Кастомные фильтры и запрет нативных select (`hz-custom-filters-ui`)
- **Строжайший запрет нативных `<select>`**: Категорически запрещено использовать нативные HTML выпадающие списки (`<select>`) и системные контролы в дашбордах, карточках, модалках и фильтрах.
- **Премиальный кастомный UI**: Все фильтры обязаны быть кастомными интерактивными компонентами (CustomSelect, Popover, FilterDropdown) в стилистике темы проекта (`bg-card`, `border-border`, `text-foreground`, `hover:bg-muted`, `bg-primary/10`).
- **Быстрый поиск внутри дропдаунов**: Если в фильтре более 5–8 элементов (города, категории, сотрудники), внутри выпадающего меню обязан быть встроен быстрый текстовый поиск.
- **Стабильная компоновка и запрет сжатия поиска**: Поле поиска никогда не должно сплющиваться в нечитаемый обрезок. Компоновать фильтры в просторные ярусы (верхний — просторный поиск и пресеты, нижний — кастомные выпадающие фильтры и переключатели).

## 31. Премиальная бренд-айдентика и модульные дизайн-системы (`hz-brandkit-identity` / `brandkit`)
- **Осознанный брендинг**: Создание премиальных визуальных систем (знаки, шрифтовые логотипы, символизм), отражающих характер проекта (финтех, кибернетика, минимализм, люкс, девелоперские инструменты).
- **Типографическая иерархия**: Точный подбор гарнитур, интерлиньяжа и трекинга; строгий баланс масштаба между акциденцией и функциональным текстом.
- **Модульная система ассетов**: Чистая векторная геометрия, масштабируемость от фавиконки 16x16 до билбордов, исключение случайных декоративных элементов.

## 32. Контекстный анти-шаблонный фронтенд (`hz-design-taste-frontend-v2` / `design-taste-frontend`)
- **Обязательный Design Read (0.B)**: Перед написанием любого UI зафиксировать целевой контекст: «Reading this as: <тип> для <аудитории> в стиле <стиль> с уклоном в <система/эстетика>».
- **Динамическая калибровка шкал**: `DESIGN_VARIANCE` (1-10), `MOTION_INTENSITY` (1-10), `VISUAL_DENSITY` (1-10) выставляются исходя из задачи (дашборд vs портфолио vs лендинг), а не берутся наугад.
- **Искоренение дефолтов ИИ**: Запрет фиолетовых «AI» градиентов/свечений (Lila ban), запрет трех одинаковых карточек, запрет Inter + slate-900, отказ от бессмысленных бесконечных зацикленных микроанимаций.

## 33. Детерминированная типографика, запрет засечек в дашбордах и полный цикл состояний (`hz-design-taste-frontend-v1` / `design-taste-frontend-v1`)
- **Проверка зависимостей перед импортом**: Всегда проверять наличие пакета в `package.json` перед вызовом.
- **Запрет Serif в дашбордах**: Для рабочих панелей и дашбордов используются строго чистые Sans-Serif и Monospace связки (Geist, Satoshi, JetBrains Mono).
- **Правило одного акцента**: В палитре используется максимум один акцентный цвет с насыщенностью < 80%.
- **Anti-Card в плотных данных**: При высокой плотности данных (`VISUAL_DENSITY > 7`) запрещено упаковывать каждую цифру в отдельную карточку; использовать разделители `divide-y`, `border-t` и структурное пространство.
- **Полный цикл состояний**: Обязательная реализация скелетонов загрузки, продуманных пустых состояний (empty states) с подсказкой действия и инлайн-ошибок.

## 34. Полный вывод кода без усечений (`hz-full-output-enforcement` / `full-output-enforcement`)
- **Категорический запрет на пропуски**: Запрещены любые комментарии вида `// TODO`, `// ... остальной код`, `/* unchanged */`, `<!-- same as before -->`.
- **Готовность к исполнению**: Код генерируется в полном объеме, готовый к немедленному исполнению и тестированию.

## 44. Канонический реестр фич и сквозной цикл тестирования/исправления (`hz-feature-matrix-qa-loop` / `/goal`)

  ```
  /goal go over every single feature in this app create a user story with expected behaviour based on the code keep a single canonical spreadsheet tracking the features status
  • when done switch loop to testing every user story and documenting all errors
  • when done fix every logistical error or ux error
  • test every user behaviour again post fix
  ```
- **Процесс исполнения цикла**:
  1. **Инвентаризация и User Stories**: Проанализировать весь код приложения до единой фичи, составить для каждой фичи пользовательскую историю (User Story) с ожидаемым поведением, граничными условиями и зафиксировать в едином каноническом spreadsheet/реестре (например, `feature_stories_spreadsheet.md` или артефакте).
  2. **Цикл сквозного тестирования**: Автоматически переключиться в режим сквозного тестирования каждой пользовательской истории, воспроизвести сценарии в коде/тестах и задокументировать все найденные сбои, регрессии и несоответствия.
  3. **Устранение ошибок**: Исправить каждую логистическую, архитектурную или UX-ошибку, выявленную на этапе тестирования.
  4. **Повторная верификация (Post-fix Test)**: Повторно протестировать каждое пользовательское поведение после внесения правок, убедиться в отсутствии регрессий и зафиксировать подтвержденный статус в каноническом spreadsheet.

## 45. 5-Уровневая Анти-Бот Защита Форм (`hz-forms-anti-bot`)
- **Обязательно для всех публичных форм**: Любая создаваемая или обновляемая форма (сбор лидов, корзина, опросники, ТЗ, калькуляторы, обратная связь) обязана оснащаться сквозной 5-уровневой защитой:
  1. **Honeypot-поле (`companyWebsite`)**: Скрытое поле (`style={{ display: 'none' }}`, `tabIndex={-1}`, `aria-hidden="true"`, `autoComplete="off"`). Заполнено -> бот.
  2. **Временная метка (>= 5 секунд)**: Фиксация timestamp монтирования (`formStartedAt`). Если форма отправлена быстрее 5 секунд — бот. Максимальный срок жизни — 24 часа.
  3. **Простая JS-проверка**: Детерминированный challenge-токен на базе timestamp, синхронно вычисляемый в JS (отсекает спам-скрипты без исполнения JS).
  4. **Rate-limit по IP + Client Fingerprint**: Двухфакторное ограничение частоты: по IP (до 12/час) и по отпечатку `ip::user-agent::accept-language` (до 4/10мин). При превышении — 429 Too Many Requests.
  5. **Серверная проверка и Silent Drop**: Обязательная проверка на сервере. При обнаружении бота сервер возвращает успешный ответ (HTTP 201 Created), но **не сохраняет данные в БД** и **не отправляет уведомления** (Telegram, CRM, email).

## 46. Обязательное использование CodeGraph в анализе кода (`hz-codegraph-first`)
- **CodeGraph First**: В репозиториях, проиндексированных CodeGraph (где существует каталог `.codegraph/` в корне проекта), ВСЕГДА использовать CodeGraph ПЕРЕД grep/find или прямым чтением файлов.
- **Инструменты доступа**:
  - **MCP tool**: `codegraph_explore` отвечает на большинство вопросов по коду за один вызов — точный исходный код релевантных символов с номерами строк и цепочки вызовов между ними (call paths), включая динамическую диспетчеризацию, которую grep не способен отследить. Назовите файл или символ в запросе для чтения исходника. Если символ указан, но отложен (deferred) — загрузить его по имени через поиск.
  - **Shell CLI**: `codegraph explore "<symbol names or question>"` выводит аналогичную структурированную информацию в терминале.
- **Порядок работы**:
  1. При исследовании архитектуры, поиске функций, классов, маршрутов, схем или отслеживании зависимостей — передать имя символа или вопрос в `codegraph_explore` / `codegraph explore`.
  2. Трассировать поток вызовов целиком, исследуя всех потребителей функции перед внесением изменений.
  3. Прямой grep/find/view_file использовать только для файлов, не входящих в AST-индекс (конфигурации, env, статика), либо если в репозитории отсутствует папка `.codegraph/`.
